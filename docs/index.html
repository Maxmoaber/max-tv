🎬 Max.tv

Plataforma web de streaming para explorar películas y series en tendencia, buscar contenido, guardar favoritos y ver tráilers — con datos reales de TMDb.

Max.tv es una aplicación cliente-servidor con un frontend React que consume una API REST propia en Node.js. El backend actúa como proxy seguro hacia TMDb (nunca se expone la API key en el cliente) y gestiona usuarios y favoritos con JWT sobre PostgreSQL (Neon).

1 Arquitectura del Sistema

Arquitectura cliente-servidor de tres capas: presentación (React), lógica de negocio (Express) y datos (PostgreSQL + TMDb).

⚛️

Frontend (React + Vite)

SPA con rutas, estado global (Context), búsqueda con debounce, favoritos optimistas y skeletons de carga. Desplegado en Netlify.

🔧

Backend (Express)

API REST con auth JWT, CRUD de favoritos y proxy hacia TMDb con caché en memoria. Desplegado en Render.

🗄️

Base de datos

PostgreSQL gestionado en la nube con Neon. Esquema definido con Prisma ORM y sincronizado con db push.

🎥

TMDb API

Fuente de contenido real: tendencias, búsqueda, detalles, créditos, tráilers e imágenes de películas y series.

2 Casos de Uso

Cada caso de uso describe el flujo completo desde la acción del usuario hasta la respuesta del sistema.

🏠

Explorar contenido en tendencia

Usuario anónimo o autenticado
  1. El usuario ingresa a la página principal /.
  2. El frontend solicita GET /api/tmdb/trending?language=es-ES al backend.
  3. El backend consulta TMDb, aplica caché (NodeCache) y devuelve las tendencias de la semana.
  4. Se muestran los primeros 4 items en el Hero (banner con tráiler de fondo si existe) y 12 en el carrusel «Tendencias».
  5. Se cargan en paralelo los carruseles por género: Comedia, Animación, Acción y Ciencia Ficción (GET /api/tmdb/genre/:id).
  6. El usuario puede navegar los carruseles, cambiar el idioma (ES/EN) o hacer clic en «Ver más» para paginar.
🔍

Buscar películas y series

Usuario anónimo o autenticado
  1. El usuario escribe en la barra de búsqueda del Header.
  2. Con debounce de 300ms, se consulta GET /api/tmdb/search?q=....
  3. Aparece un dropdown con hasta 8 sugerencias (título + póster en miniatura).
  4. Al hacer clic en una sugerencia o presionar Enter, navega a /search?q=....
  5. La página SearchResults muestra todos los resultados en grilla con filtros de idioma.
  6. Desde cualquier resultado se puede abrir el detalle o guardar como favorito.
🔐

Registrarse e iniciar sesión

Usuario no autenticado
  1. El usuario navega a /auth.
  2. Selecciona «Crear cuenta» o «Iniciar sesión».
  3. Completa email y contraseña y envía el formulario.
  4. El backend valida contra PostgreSQL: en registro hashea con bcrypt; en login compara con bcrypt.compare.
  5. Si es exitoso, firma un JWT (expira en 7 días) con { id, email }.
  6. El frontend guarda el token en localStorage y lo envía en el header Authorization: Bearer en cada petición protegida.
  7. GET /api/auth/me verifica la sesión al recargar la página.
❤️

Guardar y gestionar favoritos

Usuario autenticado
  1. El usuario pasa el mouse sobre un póster y hace clic en «Favoritos».
  2. Se envía POST /api/favorites con el token JWT y los datos { tmdbId, mediaType, title, poster }.
  3. El backend verifica el token, asocia el favorito al userId y lo persiste en PostgreSQL.
  4. En /favorites el usuario ve todos sus favoritos (pueden existir sin conexión a TMDb, porque se guardan los metadatos).
  5. Puede filtrar por tipo (película / serie) y buscar localmente en la grilla.
  6. Para eliminar: clic en el botón de favorito → DELETE /api/favorites/:id (verifica que el item pertenezca al usuario).
🎬

Ver detalle y tráiler

Usuario anónimo o autenticado
  1. El usuario hace clic en un póster (desde carrusel, favoritos o búsqueda).
  2. Se abre un modal lateral con la información básica del item.
  3. El modal carga datos adicionales: GET /api/tmdb/movie/:id o /api/tmdb/tv/:id (sinopsis, género, rating, créditos).
  4. Si hay tráiler disponible, se incrusta un reproductor de YouTube (trailerKey).
  5. El usuario puede marcar como favorito desde el modal.
  6. Se cierra al hacer clic fuera, en la ✕ o presionando Escape.

4 Endpoints de la API

💡

¿Por qué un proxy en lugar de llamar a TMDb desde el navegador? Tres razones: (1) la API key nunca se expone al cliente, (2) se centraliza el caché con NodeCache para reducir latencia y rate-limit, y (3) se transforman las respuestas a un formato uniforme que el frontend consume sin lógica extra.

5 Esquema de Base de Datos

Definido con Prisma ORM en backend/prisma/schema.prisma. Sincronizado con npx prisma db push. Dos tablas con relación 1:N.

Diagrama entidad-relación generado con Mermaid a partir de schema.prisma.

👤

Tabla User

id PK · email único · password (bcrypt) · createdAt. Almacena las cuentas registradas.

⭐

Tabla Favorite

userId FK → User · tmdbId · mediaType · title · poster. Cada fila es un favorito de un usuario.

Un usuario puede tener muchos favoritos (relación 1:N). Cada favorito guarda tmdbId + metadatos (título, póster) para poder listarlos sin volver a llamar a TMDb.

6 Instrucciones de Instalación

⚙️

Requisitos previos: Node.js 18+ · npm · API key de TMDb (gratis en themoviedb.org) · PostgreSQL (Neon o local).

Backend — Express + Prisma

# 1. Clonar
git clone https://github.com/Maxmoaber/max-tv.git
cd max-tv/backend

# 2. Dependencias
npm install

# 3. Variables de entorno
cp .env.example .env
# Editar: TMDB_API_KEY, DATABASE_URL, JWT_SECRET

# 4. Base de datos
npx prisma generate
npx prisma db push

# 5. Levantar (http://localhost:4001)
npm run dev

Frontend — React + Vite

# 1. Entrar al frontend (otra terminal)
cd max-tv/frontend

# 2. Dependencias
npm install

# 3. Variables de entorno
cp .env.example .env
# Editar: VITE_BACKEND_URL=http://localhost:4001

# 4. Levantar (http://localhost:5173)
npm run dev
✅

Verificación: abre http://localhost:4001/health (debe responder {"status":"ok"}) y luego http://localhost:5173 para ver el Home con tendencias reales de TMDb.

Pipeline de despliegue — un push a GitHub actualiza frontend y backend en paralelo.

Frontend — Netlify

  1. Conectar repo de GitHub en Netlify.
  2. Base directory: frontend
  3. Build command: npm run build
  4. Publish directory: dist
  5. Variable: VITE_BACKEND_URL = URL de Render.
  6. Los redirects SPA ya están en netlify.toml.

Backend — Render

  1. Conectar repo en Render (Web Service).
  2. Root directory: backend
  3. Build: npm install && npx prisma generate && npx prisma db push
  4. Start: node src/server.js
  5. Variables: DATABASE_URL, JWT_SECRET, TMDB_API_KEY.
  6. Bind a 0.0.0.0 (ya configurado con HOST).

10 package.json y package-lock.json

10.1 package.json (backend y frontend)

Cada subproyecto tiene su propio package.json: el manifiesto que npm usa para instalar dependencias y ejecutar scripts.

CampoFunción
name / versionIdentificador del paquete
mainPunto de entrada del servidor (solo backend: src/server.js)
scriptsdev (nodemon / vite), start, build, preview
dependenciesNecesarias en producción: express, prisma/client, react, axios…
devDependenciesSolo en desarrollo: nodemon, prisma (CLI), vite, tailwindcss…
private(frontend) Impide publicar accidentalmente en npm

⚠️ package.json se edita manualmente al agregar/quitar dependencias — o mejor, con npm install <paquete>, que lo actualiza solo.

10.2 package-lock.json

NO se edita manualmente. Lo genera npm en cada npm install. Bloquea las versiones exactas (con hashes de integridad) de todo el árbol de dependencias para que todos los entornos instalen lo mismo.

  • Debe versionarse en git → builds reproducibles.
  • Si se elimina, npm lo regenera en el próximo install (puede variar versiones).

10.3 dependencies vs devDependencies

TipoEn producciónEjemplos
dependenciesSí — se instalan con npm install --productionexpress, react, axios, bcrypt, @prisma/client
devDependenciesNo — se omiten en el deployvite, nodemon, tailwindcss, prisma (CLI)

En Render se ejecuta install de producción: por eso prisma (CLI) está en devDependencies — solo hace falta para migraciones — mientras @prisma/client sí va en dependencies porque se usa en runtime.
